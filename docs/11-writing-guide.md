# 文档写作规范

这一页写给以后修改文档的人，也包括帮忙写文档的 AI。目标只有一个：读者打开任何一页，都能看懂它在讲什么，并且能照着做。

## 每页怎么组织

- 开头两三句话说清：这页讲什么、适合谁读、读完能做什么。
- 先讲是什么、为什么，再讲怎么做。原理和步骤分开写。
- 一个主题只在一个页面里详细讲。其他页面提到它时，用一句话加链接，不要复制粘贴。
- 能用表格、编号步骤、代码块、mermaid 图说清楚的，就别写成长段落。图要画真实的机制，不要画装饰图。

## 句子怎么写

- 用完整、平实的中文句子，一句话只说一件事。
- 术语第一次出现时解释一下，或者链接到[术语表](10-glossary.md)。命令、字段名、文件名保留原文，用反引号括起来。
- 用正面说法。写“图片必须是 800×480 的六色 PNG”，不要写“不能把非 800×480 的图片当作……”。
- 语气像懂行的同事给新人讲解，不用营销腔，也不用感叹号。

## 只写现在

文档描述的是系统现在的样子，不是开发日记。下面这些都不要出现在正文里：

| 不要写 | 原因 |
|---|---|
| “已不再是 X，而是 Y”“当时……现已……” | 读者只关心现在是什么，旧做法放进 Git 历史 |
| “本轮”“今晚”“早上”“尚未实机验证”这类时间和过程词 | 过几天就过期，而且会误导 |
| 一长串免责声明，比如“不能据此认定……”“不代表……” | 把正文淹没了。设计上的限制写进[版本与已知限制](09-versions-and-limits.md) |
| 提交 SHA、文件摘要、备份路径、某天几点几分的观测 | 属于发布记录，不是说明文档 |
| 个人电脑路径、IP、密钥 | 隐私和安全问题 |

性能数字可以写，但要写成大约多少，并说明条件，例如“手机网页 GATT 传 66 KiB 约 8 秒”。

## 以代码为准

写进文档的行为、字段、数值、命令，都要在源码里核对过。核对不了的就不写。改了接口，就在同一次改动里更新对应的文档。

## 写产品，不写某一台设备

文档描述的是产品：它的设计、行为、用法和限制，对每一台相框都成立。下面这些不写进文档：

- 某台设备的序列号、设备 ID、当前装了哪个版本、现在的主人是谁；
- 开发或使用过程中遇到的具体事件，比如“某次断电后退回了旧版本”；
- 某台电脑、某块网卡、某部手机上的个别现象；
- 测试做到哪一步、谁验证过什么。

设计层面的限制（比如“启动保护不区分复位原因”）写成产品行为，放在对应的原理页，并在[版本与已知限制](09-versions-and-limits.md)里列一行。示例里用通用的值，比如设备 ID `001122334455`、版本 v1、v2。

版本号和已知限制只写在[版本与已知限制](09-versions-and-limits.md)，更新时直接改成最新情况。

## 常见的坏写法

下面这些问题在早期文档里反复出现。每条附一句当时的原文作反例，写完一页后可以对照检查。

### 把多件事压进一句话

> 显示 APP 的 START 要求 APP_READY 与所声明的首屏完成。更新写备用槽，显式激活后确认；失败或确认前重启按目录恢复。

一句话里塞了三四个机制，每个都没讲清楚。拆开写：先说 START 什么时候算成功，再单独一段讲更新流程，必要时用编号步骤或表格。

### 名词堆叠和缩写串

> 双方承诺/ECDH/HKDF、显示后功能键短按批准、NVS 持久 owner

用斜杠和顿号把一串名词并排，读者看不出它们之间是什么关系、按什么顺序发生。写成完整的句子或步骤，说清谁做了什么、结果是什么。

### 中英混写

> 核对电脑端CoC后端和实际协商结果，不能只看设备能力
> 换 owner、推图及线上安装/回滚

有标准中文说法的词就用中文（owner 写“主人”，receipt 写“回执”，fallback 写“回退”）。协议名、字段名、命令这类必须保留英文的，用反引号括起来，并和中文之间留空格。

### 自造术语不解释

> 实体显示完成、可管理故障空闲、单所有权、业务回执

这些词只在作者脑子里有定义。要么换成大白话（“屏幕真正刷新完成”“没有应用在运行，但还能通过蓝牙管理”），要么第一次出现时解释，并收进[术语表](10-glossary.md)。

### 为想象中的误解辩护

> 保留框架恢复能力与设备实际只安装一个版本并不矛盾。
> 电子纸保留图像不证明设备在线。

这类句子是在回应一个读者根本没提出的质疑。把事实正面讲清楚就够了：“断电后屏幕仍保留最后一帧画面，所以看到画面不代表相框正在运行。”写一次，放在讲显示的地方。

### 用否定句堆出规则

> 不重放不确定管理命令；不自动切换应用，也不回退 HTTP；不能把恢复当作普通 APP 安装。

一串“不……不……不能……”读完也不知道应该怎么做。改成正面描述行为：“管理命令的回复丢失时，客户端重新连接并读取状态，确认命令是否已经执行。”

### 把测试报告当说明

> Web 32/32、UI 71/71、Go make check、迁移 3/3、Windows 交叉构建……通过。

测试通过数和构建结果属于提交记录或 CI，读者读文档是为了理解和使用，不需要知道某次跑了多少项测试。

### 记录写文档的过程

> 界面由实际 Claude Code Opus 5.5 xhigh 设计后实现。

谁写的、用什么工具写的、写了几轮，和读者无关。

### 引导读者去读源码

> 后台的具体 IPC 字段和能力列表以当前代码为准，不把相似名称当作相同操作。

文档的价值就是让读者不用先读源码。该列的字段和命令直接列出来；确实太长的，指明在哪个文件、哪个函数，并说清楚它做什么。

## 写完后的检查清单

- 开头能不能让人一眼看出这页讲什么、给谁看？
- 有没有一句话超过两个意思？
- 每个术语和缩写，第一次出现时有没有解释？
- 有没有出现日期、“本轮”“当时”“已不再”之类的词？
- 有没有某台具体设备、某台电脑的情况？
- 有没有一连串否定句？能不能改成正面说法？
- 写到的命令、字段、数值，有没有在源码里核对过？
- 链接是否都能打开？
