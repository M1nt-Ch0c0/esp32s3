## 文档放在哪里

| 内容 | 正式位置 |
|---|---|
| 开发者导航、架构原则、开发规范 | `esp32s3/wiki/` |
| SDK 声明、导入与运行校验 | 宿主 `sdk/` 和实际校验器；APP 仓库同步副本 |
| 宿主 BLE 字节协议、ABI 和目录细节 | 宿主对应 reference 文档 |
| APP 业务协议、输入格式及应用示例 | photoframe 或未来具体 APP 仓库 |
| 渲染、发送客户端和部署 | ai-quota-frame |
| 实测证据 | 执行测试所对应仓库的 validation 文档，注明日期/版本/范围 |
| 会话任务、私有环境与交接快照 | 接力文件，不代替通用开发规范 |

每个仓库 README 只做自身职责的入门导航。宿主 README 不再以相框推图命令当框架主流程；APP/电脑端说明提供业务操作，框架保留必要的兼容协议参考。

## 规则的优先级和变更

用户最新指令优先。SDK/校验器是已实现 ABI 的依据；协议代码与两端测试是实际 wire contract 的证据。发现文档与实现冲突时先指出冲突，不默默扩大权限或更改版本号。

稳定规范、已批准待实现设计、历史兼容和实测快照须显式标注。不要用“本次新增”“目前已全部完成”代替具体基线和范围。新接口在代码/测试实现前写成提案，不能假定功能已存在。

接口改动同时更新参数、所有权、资源上限、错误、取消/切出行为、兼容矩阵、示例和测试。APP 协议不得只有代码而没有版本化字段说明。发布记录包含源提交和产物摘要，不包含密钥或原始敏感日志。

## 当前并行分工

文档会话使用各仓 `codex/framework-wiki`，只改 Markdown 和配置示例等文档；Mac 功能会话使用自己的功能分支继续 APP BLE 收图及实测。文档会话不拉取或覆盖 Mac 工作区，不操作设备/服务。

Mac 对实现必要的 SDK、校验器和协议参考进行最小更新，记录实际改动及证据；功能完成后协调合并 Wiki。各自选择文件提交，不用 `git add -A` 混入对方草稿，不 reset/clean、force-push 或整文件覆盖冲突。

## GitHub 发布方式

本 Wiki 的可维护原件在 `esp32s3/wiki/`。2026-10-23 的文档发布与功能开发分离；2026-10-24 按用户要求协调合入各仓 main，保留功能实现和文档历史。当前 GitHub 原生 Wiki 仓库尚未初始化，因此正式入口是仓库中的目录。

将来若启用原生 Wiki，以本目录为源同步页面与侧栏，不在两处独立修改。原生 Wiki 是单独的 Git 仓库，普通仓库推送不会自动更新它。主分支和开发分支状态也要说明，不能把“已推开发分支”称作“已合并 main”。

## 文档检查

提交前检查相对链接、所有引用的文件、代码路径、版本基线、示例语法及大小/数量/错误码与 SDK 一致；检查 diff 无真实凭据。示例工程变动时重新构建或验证对应示例。保留历史验证事实，修正入口和当前说明，不伪造历史测试结果。
