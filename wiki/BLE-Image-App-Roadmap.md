# 已批准路线：由 photoframe APP 接收 BLE 图片

[返回首页](Home.md) · [应用 BLE](Application-BLE.md)

**状态更新：2026-10-24 APP 收图实现及配套客户端合入各仓 main。** 已完成部分实机验证，完整生命周期、最终目测及长期稳定性仍待验收，详见 [已核实进度](Status-and-Evidence.md)。本页保留开发与验收要求。

## 职责决定

| 部分 | 责任 |
|---|---|
| 宿主 | 常驻发现、无线栈、认证、受管 GATT、应用 OTA/热加载/切换、统一调度、硬件显示 |
| photoframe APP | 图片传输状态、分块组装、长度/SHA/PNG 校验、超时/断开处理、显示完成回执 |
| Mac 客户端 | 找到已认证设备与当前相框服务，分块发送、处理错误、查询同一请求的结果 |

用户接受先按键切到相框 APP 再发送；客户端不能自动抢回选择权。切出后收图服务停止，常驻发现和应用 OTA 继续工作。

## 复用接口与能力审计

优先使用 ABI 2.1 注册/设置/注销接口、BLE 事件和签名应用特征读写。每值 128 字节，因此需要 APP 分块；不是为了图片大小直接扩大通用特征值。显示走已有 `app_host_display_v2()`，解码复用相框已有实现。

先审查 malloc/PSRAM、事件预算、断开和 STOP 清理、同步显示后读取回执、HTTP INPUT 并发及协议摘要实现。若缺少通用能力，提交最小扩展提案：缺口代码证据、无法仅在 APP 解决的原因、ABI 兼容性、资源上限、所有权、清理和测试。暂停继续增加专用 PNG 宿主 opcode 或串口刷写宿主。

## APP 协议评审必须核对

1. 协议版本、字节序、服务/特征 UUID、请求与响应字段及最大长度是什么？
2. BEGIN 如何携带请求 ID、大小和摘要？如何拒绝非法尺寸和资源不足？
3. CHUNK 如何处理相同重复、冲突重复、空洞、越界和已完成请求？
4. 查询、取消、接收超时、断开、STOP、重新连接和重新加载各自保留什么？
5. SHA 与完整 PNG 验证何时发生？失败是否保证尚未显示？
6. COMMIT 回复丢失时如何查询同一回执？APP 代次改变或回执丢失时如何停止自动重画？
7. 业务错误与 APP_ERR_RUNTIME、宿主 BLE 错误怎样区分？
8. HTTP 输入、计时事件、OTA 和按键到来时如何处置跨事件的接收状态？

正式应用协议见 [photoframe/docs/ble-image-input.md](https://github.com/M1nt-Ch0c0/photoframe/blob/main/docs/ble-image-input.md)，实测见 [APP 验收记录](https://github.com/M1nt-Ch0c0/photoframe/blob/main/docs/validation-ble-input-2026-10-23.md)。框架 Wiki 不取代 APP 字节协议原件。

## 验收清单

- 原生测试覆盖鉴权路由、分块边界、摘要、坏 PNG、内存失败、状态机、断开/STOP、重复提交和回执丢失。
- 通过既有 BLE 应用 OTA 安装新 ABI 2.1 相框，显式激活并保留旧 active 可回退。
- Mac 从发现到 APP 收图和完成确认，全程无需设备 IPv4；验证无 HTTP 回退。
- 测试 APP 非当前时明确不可用，切出服务消失、旧代次请求失效，常驻 OTA 仍可用。
- APP 通过宿主显示，取得可信业务完成回执，并经人工目测方向、颜色、内容。
- 丢回复恢复严格证明没有第二次刷新；不能把旧宿主图片通道测试计入此项。
- 验证更新/回滚、内存释放和启动保护；报告实际版本、bin/ELF/包大小及内部 RAM/PSRAM 峰值。

旧宿主通道代码与有效测试保留作兼容基线。删除它、引入宿主整机 OTA 或更改分区表均不是本路线的隐含任务。
