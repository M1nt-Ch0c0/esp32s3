# 术语与常见问题

[返回首页](Home.md)

## 这是一个 OS 吗？

它有应用加载、生命周期、服务、通信和更新等小型 OS 式能力，实际基于 ESP-IDF/FreeRTOS。APP 是共享地址空间的原生 ELF，不是隔离进程，不具备完整操作系统的权限和内存保护。

## 固件、APP 和 ABI 有什么区别？

宿主固件 `.bin` 刷入 factory，提供框架；APP `.app.elf` 通过数据槽更新，提供业务；ABI 是两者约定的函数和数据布局。三个部分都是本项目维护的，ABI 不是厂商固定不变的等级。

APP 包的发布版本如 v20 与 ABI 2.2 相互独立。同一 ABI 内可以发布多个版本，发布版本号本身不表示接口能力。源码默认是 ABI 2 不会自动改变设备已经安装的旧包。

## 2.2 SDK 为什么还能声明旧 ABI？

`APP_MANIFEST` 保持 2.0，旧 APP 不会自动依赖新服务；GATT 小消息使用 `APP_MANIFEST_BLE` 声明 2.1，CoC 使用 `APP_MANIFEST_COC` 声明 2.2。只改版本数字不能把旧 PNG 入口变成事件式 APP。

## GATT、服务、特征是什么？

GATT 是 BLE 交换应用数据的组织方式。服务将一组能力放在一起；特征提供某个可读、可写或可通知的数据项。宿主公开常驻管理服务，当前 APP 可登记自己的受管服务。特征 UUID 是身份，协议版本与应用 ID 则各有不同用途。

## 为什么 APP 不自己操作 NimBLE 或开线程？

应用会被热卸载。任意系统回调或后台线程可能在卸载后继续调用已释放代码。宿主管理回调和资源，以复制的数据和合作式事件通知 APP，切出时统一取消。

## BLE 发现成功，HTTP 为什么仍失败？

v2 宿主的旧 HTTP 控制入口返回 410；这是移除固定 token 入口的预期结果。发现本身也不会打通路由、客户端隔离或跨网段。现有兼容 BLE 图片通道可不依赖 IP；用户确定的新路线进一步将收图状态机放到 APP。电脑取额度仍需联网，设备本身可以无 Wi-Fi。

## 通用 Wi-Fi APP 请求接口在哪里？

当前没有。宿主管 Wi-Fi 配置和连接（旧 HTTP 控制在 v2 已退役为 410），并向 APP 通知网络状态。未来 APP 若需要联网取数据，要先提出最小通用服务设计，不能直接导入 socket 或将规划写成已实现。

## 上传成功为什么不等于显示成功？

暂存只说明完整性或存储通过。显示完成必须等面板刷新和最终 POWER_OFF 成功，再生成对应业务的可信回执，最后人工核对画面。电子纸会断电保留旧图。

## 更新相框需要重新刷宿主吗？

已有宿主支持所需 ABI 时通过应用 OTA 更新 ELF。只有确实缺少通用宿主能力并完成审计后才考虑框架变更；从旧宿主迁移到 ABI 2.2 CoC 需要更新一次宿主；2026-10-27 已授权的更新仅写 factory，保留分区表、配置与应用槽。项目没有宿主整机 OTA。

## CoC 为什么比旧 GATT 图片路径快？

旧路径每块图片只有 106 字节，写入后还要读取业务回执。CoC 使用大记录、连续发送和额度背压，成功 CHUNK 不逐块往返。实测 67,509 字节发送阶段 2.477 秒，刷屏另计；上传进度不是显示完成证据。

## 能从 POWERON 判断是不是没电吗？

不能。复位原因和 uptime 可以证明重启，但当前固件没有电池电压、剩余电量或 PMIC 关机原因遥测。缺失的数据必须显示未知，不能凭蓝牙离线或残留画面推断。

## README 里为什么还有旧接口？

当前说明应以角色和新开发规范为主；旧 `/api/push` 只保留历史参考，v2 控制入口返回 410；宿主图片 opcode 保留兼容参考。测试记录按发生时的版本保存，不应被误当成新 APP 的开发教程。

## 为什么没有设备推图令牌输入？

配对 v2 改为双方协商并由相框功能键批准，之后保存关系。长按 GPIO4 功能键至少八秒并松开可重置 owner，BOOT/电源键不参与。浏览器和原生后台是不同 owner，切换控制端需物理重置并重新配对。当前发布尚未实机验证。
